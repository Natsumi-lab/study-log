# 検出事項（ファインディング）の構造化と監査所見の導出手順
（判定プロセス編 第1部）

---

## 1. 監査証拠から監査所見・監査意見への全体フロー

情報セキュリティ監査において、入手した個々の監査証拠をそのまま報告書に並べるだけでは監査所見にはなりません。監査人は客観的証拠を分析・評価し、事実認定を経て論理的な「検出事項（ファインディング）」へと構造化する必要があります。

```
┌─────────────────────────────────────────────────────────────┐
│ ① 監査手続の実施と証拠収集 (閲覧、観察、再実施等)          │
└──────────────────────────┬──────────────────────────────────┘
                           ▼
┌─────────────────────────────────────────────────────────────┐
│ ② 事実認定 (客観的事実の確定・ファクトファインディング)    │
└──────────────────────────┬──────────────────────────────────┘
                           ▼
┌─────────────────────────────────────────────────────────────┐
│ ③ 検出事項 (ファインディング) の構造化 ★本資料の対象       │
│    [基準] - [事実] - [ギャップ] - [原因] - [影響]           │
└──────────────────────────┬──────────────────────────────────┘
                           ▼
┌─────────────────────────────────────────────────────────────┐
│ ④ 監査所見の形成 (重要性・影響度に応じた指摘事項・推奨事項) │
└──────────────────────────┬──────────────────────────────────┘
                           ▼
┌─────────────────────────────────────────────────────────────┐
│ ⑤ 監査報告・意見表明 (保証型 / 助言型)                      │
└─────────────────────────────────────────────────────────────┘
```

---

## 2. 検出事項（ファインディング）の5要素モデル

監査結果として不備や課題（検出事項）を客観的・説得力を持って提示するために、以下の**5つの構成要素（5 Elements of an Audit Finding）**に沿って情報を整理・構造化します。

```
┌─────────────────────────────────────────────────────────────┐
│ 1. 基準 (Criteria)  ：本来あるべき状態 (管理基準・規程)     │
│ 2. 事実 (Condition) ：実際の状態 (証拠で裏付けられた現状)   │
├─────────────────────────────────────────────────────────────┤
│ 3. 差異 (Gap)       ：基準と事実の乖離 (不適合・不備の内容) │
├─────────────────────────────────────────────────────────────┤
│ 4. 原因 (Cause)     ：なぜギャップが生じたのか (根本原因)   │
│ 5. 影響 (Effect)    ：放置すると何が起きるか (リスク・損害) │
└─────────────────────────────────────────────────────────────┘
```

### 5要素の詳細定義と具体例

| 構成要素 | 定義・役割 | 具体的事例（退職者アカウント管理の不備） |
| :--- | :--- | :--- |
| **① 基準（Criteria）** | 組織が遵守すべき規範、セキュリティ管理基準、社内規程、契約条件など（「どうあるべきか」）。 | 情報セキュリティ社内規程第X条：「退職者のアカウントは、人事発令日（退職日）当日に速やかに停止または削除されなければならない。」 |
| **② 事実（Condition）** | 監査手続によって客観的証拠に基づき立証・認定された現状（「実際はどうなっているか」）。 | 過去6ヶ月間の退職者20名のうち、4名のアカウントが退職後1ヶ月以上経過してもActive Directory上で有効な状態のまま残存していた（人事異動記録とADログの突合により確認）。 |
| **③ 差異・ギャップ（Gap）** | 「基準」と「事実」を対比した結果生じる差異、不備、統制の欠陥。 | 退職日当日にアカウントを即時無効化する運用ルールが遵守されておらず、未抹消のアカウントが存在する。 |
| **④ 原因（Cause）** | なぜそのギャップが生じたのか、その根本的な背景や統制上の不備理由（「なぜ起きたのか」）。 | 人事部門から情報システム部への退職通知フローが月次集約（毎月末）となっており、退職発生時の即時連絡連携プロセスが未整備であったため。 |
| **⑤ 影響（Effect）** | ギャップが存在することによって組織が被る潜在的または顕在的な損失・リスク（「何が問題か」）。 | 元従業員による社内システムへの不正アクセス、機密情報・個人データの漏えい、不正操作に伴う業務妨害等の重大なセキュリティ侵害リスクが存在する。 |

---

## 3. 根本原因の分析（Root Cause Analysis）と改善提言（推奨事項）

監査人は単に「事実と基準のギャップ」を指摘するだけでなく、**「原因（Cause）」を正確に特定することで、実効性のある改善提言（推奨事項：Recommendation）を導く**必要があります。

* **対症療法的な指摘の回避:**
  * ❌ *不十分な指摘:* 「残存していた4つのアカウントを直ちに削除しなさい。」（再発防止にならない）
  * ⭕ *根本原因にアプローチした推奨:* 「人事システム上の退職処理とID管理システムのプロビジョニング機能を自動連携させるか、人事発令と同時に情シス部門へ即時通知される緊急連絡フローを構築・運用ルール化されたい。」
* **改善の実行責任の所在:**
  * 監査人は具体的な改善の方向性（推奨事項）を提示するが、**具体的な改善計画の立案および実行は「被監査主体（経営者・運用部門）」の責任**である（監査人が直接設定を変更・代行することは独立性違反）。

---

## 4. 試験対策用：重要キーワード・引っかけパターン

1. **事実認定における証拠の必須性**
   * *誤答例*：「被監査部門の担当者が『一部のアカウント削除が遅れたかもしれない』と供述したため、実態のログ突合を行わずに検出事項として確定した」  
     → **×（供述のみで事実認定してはならず、人事リストとシステムログ等の客観的証拠による裏付けが不可欠）**
2. **原因と結果（影響）の混同**
   * *誤答例*：「情報漏えいリスクが高まっていることを、ファインディングにおける『原因（Cause）』として記録した」  
     → **×（情報漏えいは放置した場合の『影響（Effect）』であり、原因は『通知フローの不備』などのプロセスの欠陥である）**
3. **5要素の網羅性**
   * *誤答例*：「助言型監査においては、基準と事実のギャップのみを記述すれば足り、原因分析や影響の評価は省略してよい」  
     → **×（実効性のある改善提言を導くため、助言型監査こそ原因分析とリスク影響度の評価が極めて重要となる）**
