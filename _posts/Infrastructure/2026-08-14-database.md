# 高パフォーマンスなアーキテクチャの設計（データベース）の要点まとめ

AWSにおける「高パフォーマンスなアーキテクチャの設計（Design High-Performing Architectures）」において、  
データベースの選定と最適化は、クエリレイテンシーの削減、高スループットの維持、スケーラビリティの確保に直結する極めて重要な要素です。

ワークロード（OLTP / OLAP / NoSQL / キャッシュ）に最適なデータベースサービスの選択基準とパフォーマンス向上の設計パターンを整理しました。

---

## 1. ワークロード別のデータベース選定

要件に応じた適切なデータベースタイプ（Purpose-Built Databases）の選択が基本となります。

| データベースサービス | タイプ | 主な用途・特徴 | パフォーマンスのポイント |
| :--- | :--- | :--- | :--- |
| **Amazon Aurora** | リレーショナル (OLTP) | クラウドネイティブな高性能RDB（MySQL/PostgreSQL互換）。 | 標準MySQLの最大5倍、PostgreSQLの最大3倍のスループット。ストレージ自動拡張。 |
| **Amazon RDS** | リレーショナル (OLTP) | フルマネージドな標準RDB（PostgreSQL, MySQL, MariaDB, Oracle, SQL Server）。 | リードレプリカによる読み取り分散、インスタンスクラス・EBS(gp3/io2)のスケール。 |
| **Amazon DynamoDB** | NoSQL (Key-Value / ドキュメント) | 規模に関わらず1桁ミリ秒の応答速度を提供する完全マネージドNoSQL。 | パーティションキー設計による負荷分散、オンデマンド/プロビジョンドキャパシティ。 |
| **Amazon Redshift** | データウェアハウス (OLAP) | ペタバイト規模の複雑な分析クエリを実行する列指向ストレージDB。 | 列指向フォーマット、超並列処理 (MPP)、Redshift SpectrumによるS3直接クエリ。 |
| **Amazon ElastiCache** | インメモリキャッシュ | Redis / Memcached 互換の超高速インメモリデータストア。 | マイクロ秒単位の超低遅延、DBの読み取り負荷軽減。 |
| **Amazon MemoryDB** | インメモリDB | Redis互換で超高速かつデータ耐久性（マルチAZトランザクションログ）を持つDB。 | マイクロ秒の読み取り、1桁ミリ秒の書き込み、永続化を両立。 |

---

## 2. Amazon RDS / Aurora のパフォーマンス最適化

リレーショナルデータベースにおけるボトルネック解消とスループット向上の設計です。

### リードレプリカ (Read Replicas) による読み取りスケーリング
* **仕組み**: プライマリDBから**非同期レプリケーション**でデータを複製する読み取り専用インスタンス。
* **ユースケース**: 読み取り負荷（SELECTクエリ）が集中するWebアプリケーション。
* **特徴**:
  * 最大15台（Aurora）または最大5〜15台（RDS）まで作成可能。
  * クロスリージョンに配置してグローバルな読み取り低レイテンシー化も可能。
  * ※ マルチAZ（スタンバイ）は障害対策用であり、読み取りトラフィックの分散には利用不可。

### Amazon RDS Proxy
* **仕組み**: アプリケーションとRDS/Auroraの間に配置される完全マネージド型データベースプロキシ。
* **効果**:
  * **コネクションプーリング**: 多数のサーバーレス関数（Lambda等）からの同時接続によるDBコネクション枯渇（CPU/メモリ圧迫）を防止。
  * **フェイルオーバー時間の短縮**: フェイルオーバー時の切り替え時間を最大66%短縮し、接続を維持。

## 3. Amazon DynamoDB のパフォーマンス最適化

大規模なスケールと超高速な応答速度を両立させるための設計手法です。

### パーティション設計とスロットリング防止
* **均等なアクセス分散**: パーティションキーのカーディナリティ（種類）を高く設計し、特定のパーティションにアクセスが集中する「ホットパーティション」を回避する。

### DynamoDB Accelerator (DAX)
* **概要**: DynamoDB専用の完全マネージド型インメモリキャッシュクラスター。
* **パフォーマンス**: 応答時間をミリ秒単位から**マイクロ秒単位**へ短縮。
* **特徴**: アプリケーション側のコード変更を最小限（SDKのエンドポイント切り替えのみ）にして導入可能。読み込みヘビーなワークロードに最適。

### グローバルセカンダリインデックス (GSI) と ローカルセカンダリインデックス (LSI)
* **LSI**: テーブル作成時のみ定義可能。同じパーティションキーで異なるソートキーを検索。
* **GSI**: テーブル作成後も追加可能。異なるパーティションキーとソートキーで高速検索を実現。

## 4. キャッシュ戦略によるデータベース負荷軽減

データベースの手前にインメモリキャッシュを配置し、クエリの実行回数自体を減らすパターンです。

```
[ ユーザー / アプリ ] ──① クエリ──> [ Amazon ElastiCache ] ──(ヒット: 即時返却 / マイクロ秒)
                             │
                             └─② キャッシュミス時──> [ Amazon RDS / Aurora ]
```

### キャッシュパターン
1. **Lazy Loading (遅延読み込み / Cache-Aside)**:
   * アプリがまずキャッシュを確認し、ミスした場合のみDBから取得してキャッシュに書き込む。不要なデータがキャッシュに入らないが、キャッシュミス時の初回レイテンシーが発生。
2. **Write-Through (ライトスルー)**:
   * データをDBに書き込むと同時にキャッシュにも書き込む。キャッシュのデータが常に最新に保たれるが、書き込みオーバーヘッドが発生。

## 5. データベース選定フロー（要件別）

```
[ データベース要件の整理 ]
├─ 高度な結合(JOIN)・トランザクション重視 ───────> Amazon Aurora / RDS
│   ├─ 読み取り負荷が高い ──────────────────> リードレプリカを追加
│   └─ Lambdaなどからの大量コネクション ──────> RDS Proxy を導入
├─ 超高頻度アクセス・水平スケール (Key-Value) ────> Amazon DynamoDB
│   └─ マイクロ秒の読み取りが必要 ───────────> DynamoDB Accelerator (DAX)
├─ 頻出クエリの超低遅延化・セッション管理 ───────> Amazon ElastiCache (Redis)
└─ 大規模集計・複雑なデータ分析 (OLAP) ────────> Amazon Redshift
