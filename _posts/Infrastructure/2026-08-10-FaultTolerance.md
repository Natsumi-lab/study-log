# 弾力性に優れたアーキテクチャの設計（耐障害性）の要点まとめ

AWSにおける「弾力性に優れたアーキテクチャの設計（Design Resilient Architectures）」は、  
システム障害やトラフィックの急増が発生した場合でも、サービスを停止させずに自動で復旧・拡張できるインフラを構築するためのコアコンセプトです。

---

## 1. 弾力性（Resiliency）と耐障害性（Fault Tolerance）の基本概念

* **高可用性 (High Availability)**: 障害が発生してもシステム全体が停止せず、稼働し続ける能力（マルチAZ構成など）。
* **耐障害性 (Fault Tolerance)**: コンポーネントに障害が発生しても、ユーザー体験に影響を与えずに正常動作を維持する設計。
* **弾力性 (Elasticity)**: 需要の変動（トラフィックの急増・減少）に合わせて自動的にリソースを増減させる能力（Auto Scalingなど）。
* **可溶性と回復性の設計方針**: 「単一障害点（SPOF: Single Point of Failure）の排除」と「疎結合（Loose Coupling）アーキテクチャ」が最重要テーマ。

---

## 2. 疎結合アーキテクチャ（Loose Coupling）の実現

コンポーネント同士を直接連結（密結合）させず、非同期でメッセージを仲介させることで、一方の障害が他方に波及するのを防ぎます。

### 代表的な非同期処理パターンとサービス

```
[ Web API ] ──> ( Amazon SQS / SNS / EventBridge ) ──> [ ワーカー処理 / Lambda ]
```

* **Amazon SQS (Simple Queue Service)**:
  * メッセージをキューに保持し、後続の処理（ワーカーなど）が自身のペースで処理する（デカップリング）。
  * ワーカーがダウンしてもメッセージはキューに保持されるため、データの喪失を防ぐ。
* **Amazon SNS (Simple Notification Service)**:
  * 1つのイベントを複数の宛先へ同時に通知・配送する（Pub/Sub モデル）。
* **Amazon EventBridge**:
  * スケジュール起動やAWSサービス間のイベント駆動型アーキテクチャを容易に構築。

---

## 3. 自動リカバリとセルフヒーリング（Self-Healing）

障害検知から復旧までのプロセスを自動化し、運用介入なしで正常状態へ復帰させます。

* **ロードバランシングとヘルスチェック (ELB)**:
  * ALB/NLB がターゲット（EC2インスタンス）の正常性を定期確認。
  * 不健全（Unhealthy）と判断されたインスタンスへのトラフィック割り振りを自動停止。
* **Auto Scaling による自動インスタンス置き換え**:
  * ELB ヘルスチェックと連携し、不健全なインスタンスを自動終了して新しいインスタンスを起動。
* **Amazon Route 53 (DNS フェイルオーバー)**:
  * ヘルスチェック機能を用いて、障害発生時に別リージョンや別エンドポイント（S3の静的ウェブサイトなど）へトラフィックを自動切り替え。

---

## 4. データベースとストレージの耐障害性設計

データの完全性と可用性を維持するための構成設計です。

| サービス | 耐障害性・高可用性の仕組み | RTO / RPO |
| :--- | :--- | :--- |
| **Amazon RDS (Multi-AZ)** | プライマリDBからスタンバイDBへ自動同期複製。障害時はDNS切り替えで自動フェイルオーバー。 | RTO: 数分 / RPO: ほぼ0 |
| **Amazon Aurora** | 3つのAZに跨って6つのデータコピーを保存。2つのコピーが失われても書き込み維持、3つ失われても読み込み維持。 | RTO: 数秒〜数分 / RPO: ほぼ0 |
| **Amazon DynamoDB** | データを自動的に3つのAZへ同期複製。グローバルテーブルを使用することでマルチリージョンでのアクティブ/アクティブ構成も可能。 | RTO: 0 / RPO: 0 |
| **Amazon S3** | 標準クラスターで3つ以上のAZに分散配置（11 9s の耐久性）。クロスリージョンレプリケーション（CRR）で災害対策（DR）にも対応。 | 高い耐久性 |

---

## 5. ステートレスアーキテクチャ（Stateless Architecture）

サーバー自体にセッション情報や状態を持たせないことで、インスタンスの追加・削除・破棄を自由に行えるようにします。

* **セッション情報の分離**:
  * ユーザーのログイン状態やカート情報を EC2 内に保持せず、**Amazon ElastiCache (Redis/Memcached)** や **Amazon DynamoDB** に外部化。
* **静的コンテンツと動的コンテンツの分離**:
  * 静的ファイル（画像・JS・CSS）は **Amazon S3** に配置し、**Amazon CloudFront** から配信。

---

## 6. 災害対策（Disaster Recovery: DR）戦略

リージョン規模の大規模障害や自然災害に対処するための4つの基本パターンです。

```
[ コスト低 / RTO・RPO長 ] ────────────────────────────────────> [ コスト高 / RTO・RPO最小 ]

 1. バックアップ＆リストア   2. パイロットライト   3. ウォームスタンバイ   4. マルチサイト（アクティブ/アクティブ）
 (Backup & Restore)        (Pilot Light)        (Warm Standby)        (Multi-Site Active-Active)
```

1. **バックアップ＆リストア (Backup & Restore)**:
   * データを別リージョンに定期バックアップし、被災時にインフラを構築して復元（最も安価、復旧に時間がかかる）。
2. **パイロットライト (Pilot Light)**:
   * コア部分（DBなど）のみを別リージョンで常時稼働・同期させ、被災時にその他のWeb/APサーバーをスケールアウトして全系起動。
3. **ウォームスタンバイ (Warm Standby)**:
   * 最小限の構成（縮小版）で別リージョンにて常時稼働させておき、被災時にAuto Scaling等でフルサイズへ急速拡張。
4. **マルチサイト・アクティブ/アクティブ (Multi-Site Active-Active)**:
   * 複数のリージョンで全系リソースを常に稼働させ、Route 53のトラフィックルーティングで分散処理（最も高コスト、即時復旧）。
