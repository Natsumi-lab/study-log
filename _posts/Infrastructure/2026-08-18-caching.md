# 高パフォーマンスなアーキテクチャの設計（キャッシュの選定）の要点まとめ

AWSにおける「高パフォーマンスなアーキテクチャの設計（Design High-Performing Architectures）」において、  
キャッシュ（Caching）戦略は、バックエンドリソースやデータベースへの負荷を劇的に低減し、  
ミリ秒からマイクロ秒単位の超低遅延なレスポンスを実現するための最重要設計要素です。

アーキテクチャのどの階層（エッジ、Web/AP、データベース）にどのキャッシュサービスを配置すべきかの選定基準をまとめました。

---

## 1. キャッシュの配置階層と全体像

キャッシュは適切な階層に配置することで最大の効果を発揮します。

```
[ ユーザー (クライアント) ]
       │
       ▼
[ エッジ階層 ] ──────── Amazon CloudFront (CDN) / Lambda@Edge / CloudFront Functions
       │
       ▼
[ Web / AP 階層 ] ───── API Gateway キャッシュ / EC2 ローカルキャッシュ
       │
       ▼
[ DB キャッシュ階層 ] ─ Amazon ElastiCache (Redis / Memcached) / DynamoDB Accelerator (DAX)
       │
       ▼
[ 永続化ストレージ ] ── RDS / Aurora / DynamoDB / S3
```

---

## 2. エッジ階層：Amazon CloudFront

地理的にユーザーの近くにあるエッジロケーションを利用してコンテンツをキャッシュ・配信するサービスです。

* **主な役割**:
  * 静的コンテンツ（画像、動画、CSS/JS）および動的APIレスポンスのキャッシュ。
  * オリジンサーバー（S3、ALB、EC2など）へのアクセス負荷とネットワーク遅延の低減。
* **主要な最適化設定**:
  * **TTL (Time to Live)**: キャッシュの保持期間（最小・最大・デフォルト）を制御。
  * **Cache Behaviors（キャッシュ動作）**: パスパターンごとに異なるキャッシュポリシーやオリジンを割り当て。
  * **キャッシュ無効化 (Invalidation)**: コンテンツ更新時にエッジのキャッシュを強制破棄（ワイルドカード `/*` も指定可能）。
  * **Origin Shield**: エッジとオリジンの間に追加のキャッシュ層を設けてオリジン負荷を極小化。

---

## 3. Web / API 階層：Amazon API Gateway キャッシュ

REST API のレスポンスをステージ単位でキャッシュする機能です。

* **主な役割**:
  * バックエンド（Lambda、HTTPバックエンド）への重複呼び出しを防ぎ、APIの応答速度を向上。
* **特徴**:
  * キャッシュキー（クエリパラメータやヘッダーなど）に基づいてレスポンスを保持。
  * バックエンドの実行回数を減らすことで、Lambda等の実行コスト削減にも直結。

---

## 4. DB 階層：Amazon ElastiCache（Redis vs Memcached）

リレーショナルデータベース（RDS/Aurora）やバックエンドの手前に配置するインメモリキャッシュです。  
SAA試験では **Redis** と **Memcached** の機能差による選定が最頻出です。

| 比較項目 | Amazon ElastiCache for Redis | Amazon ElastiCache for Memcached |
| :--- | :--- | :--- |
| **複雑なデータ構造** | 対応（文字列、リスト、セット、ハッシュ、ソート済みセット等） | 非対応（シンプルな Key-Value のみ） |
| **高可用性・フェイルオーバー** | **対応**（マルチAZ、自動フェイルオーバー） | 非対応（障害時はノードが再起動） |
| **データの永続性 (Persistence)** | **対応**（スナップショット AOF/RDB によるバックアップ・復元） | 非対応（揮発性、再起動で消失） |
| **レプリケーション** | **対応**（プライマリ ↔ リードレプリカ構成） | 非対応 |
| **マルチスレッド処理** | シングルスレッド（水平スケール/クラスター構成） | **マルチスレッド対応**（垂直スケールに強い） |
| **主なユースケース** | ランキング機能（Leaderboard）、セッション管理、Pub/Sub、地理空間情報 | 純粋なオブジェクトキャッシュ、シンプルなHTML断片のキャッシュ |

---

## 5. DB 階層：Amazon DynamoDB Accelerator (DAX)

Amazon DynamoDB 専用のフルマネージド・高可用性インメモリキャッシュです。

* **パフォーマンス**:
  * DynamoDB のレスポンス（ミリ秒単位）を**マイクロ秒単位（最大10倍高速）**に短縮。
* **特徴**:
  * **コードの互換性**: アプリケーションコードのロジックを変更することなく、DynamoDB SDK のエンドポイントを DAX クラスターに向けるだけで利用可能。
* **ユースケース**:
  * 読み込み負荷が非常に高いワークロード（ECサイトのトップページ商品情報、オークション等）。

---

## 6. キャッシュ戦略（書き込み・読み込みパターン）

| キャッシュ戦略 | 動作概要 | メリット | デメリット / 考慮点 |
| :--- | :--- | :--- | :--- |
| **Lazy Loading (Cache-Aside / 遅延読み込み)** | アプリがキャッシュを確認し、ミスした場合のみDBから取得してキャッシュに格納。 | 実際に要求されたデータのみがキャッシュされる（省メモリ）。 | 初回アクセス（キャッシュミス時）に遅延が発生。データ更新時の不整合対策（TTL設定）が必要。 |
| **Write-Through (ライトスルー)** | データをDBに書き込むと同時にキャッシュにも書き込む。 | キャッシュ内のデータが常に最新で高速。 | 書き込み処理のレイテンシー増加。参照されないデータもキャッシュを消費する。 |

---

## 7. キャッシュ選定フロー（要件別）

```
[ キャッシュ選定フロー ]
├─ グローバル配信・静的/動的Web配信の高速化 ────────> Amazon CloudFront
├─ REST API のバックエンド呼び出し削減 ──────────────> API Gateway キャッシュ
├─ NoSQL (DynamoDB) のマイクロ秒化 ──────────────────> DynamoDB Accelerator (DAX)
└─ RDB等の汎用インメモリキャッシュ (ElastiCache)
    ├─ 複雑なデータ型、高可用性(マルチAZ)、永続化が必要 ─> ElastiCache for Redis
    └─ 単純なKey-Value、マルチスレッド処理重視 ────────> ElastiCache for Memcached
```
